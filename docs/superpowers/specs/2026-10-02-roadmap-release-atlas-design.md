# Release atlas design

Approved direction: concept A, selected by the user on 2026-10-02. The user authorized execution and asked to skip the design interview.

Versions are destinations; tasks are roadwork. Keep the Evergreen highway identity and both local HTML pages, with no framework or build step. Replace nested milestone/task versions with flat tasks referencing `targetRelease`. Preserve existing task IDs as internal deep-link keys. A task may have `shippedIn` only when its work actually shipped. Store release planning fields in `releasePlans`, keyed by version, so all existing released records remain unchanged, including legacy milestone links. Each plan has `title`, `goal`, `done_when`, and `scope` (`contained`, `medium`, `large`). One top-level `activeRelease` identifies the current destination. Task array order controls sequencing; optional numeric `stage` and `label` improve local presentation without changing identity.

Completing work does not ship software. `done` records completion and references; `release VERSION` requires all included tasks complete, an explicit validation statement and release writing. It records the release and shipping references, never creates Git tags or pushes. Patch releases can include several completed tasks drawn from an upcoming destination; patch numbers are allocated only for a concrete release. Finishing the last task makes its destination ready, not released. Retargeting completed shipped work is prohibited through routine helpers.

The atlas separates compressed historical families from upcoming scope regions. Future widths are fixed by broad scope, independent of task count. Tasks are stacked vertically within a highway if necessary, keeping every task selectable. Dropped tasks appear on subdued spurs and are excluded from progress; completed tasks have checks, active work has explicit status, future work has dashed markers. Release landmarks join participating highways only. The browser construction lane starts within the 3.0 region, with its launch marked at 3.0. `YOU ARE HERE` identifies the current release region; the last shipped version is a separate label. History can expand and every release remains accessible in the itinerary and via existing version hashes. No spatial percentage or time estimate is implied.

Task board groups by target release, shows task names and stages, and keeps status/highway/story/search filters and internal deep links. Story coverage distinguishes work completed from work shipped. Minimal briefs show current tasks and target releases; medium briefs add current goals, remaining work, recent completions and five recently shipped releases; maximum briefs retain a complete JSON snapshot.

Migration preserves every released object, task ID, note, reference, status and original log entry. It removes only unreleased patch records tied to task planning numbers. All old group goals and completion criteria survive in release plans. Historical task versions become `shippedIn` only for done tasks with a released match. Future task versions disappear; V2 stages target 2.0, tense targets 2.1 and browser targets 3.0. Stage prefixes move to numeric stage metadata. Preserve the existing 1.1.14 release record despite the absent local tag; report that discrepancy without manufacturing or rewriting tags.

Validation checks schema, release/task references, unique IDs, stages, area ownership, real shipping, release readiness, writing lengths, dates, logs and active destination. Migration must be idempotent and demonstrate unchanged released records and historical task content. Existing dirty work is preserved. Do not ship, tag, commit unrelated changes or push as part of this implementation.
